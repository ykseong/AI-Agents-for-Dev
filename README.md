# AI Agents for Dev

멀티 에이전트 기반 소프트웨어 개발 자동화 시스템. 9개의 전문 에이전트가 역할을 분담하여 사용자의 요청을 실제 동작하는 소프트웨어로 만들어낸다.

---

## 사용자 인터페이스: 어떻게 작업을 요청하는가

사용자는 **PL Agent** 하나와만 대화한다. 나머지 에이전트는 사용자에게 직접 노출되지 않으며, 시스템 내부에서 자율적으로 협업한다.

### 요청 방식

작업 요청은 자연어로 작성하며, 요청의 성격에 따라 세 가지 유형으로 분류된다.

#### 유형 1 — 신규 개발 요청

무엇을 만들지와 핵심 요구사항을 함께 전달한다. 기술 스택이나 구현 방식은 명시하지 않아도 된다.

```
"할 일 목록 앱을 만들어줘.
 - 할 일 추가, 완료 처리, 삭제 기능이 있어야 해
 - 브라우저를 닫아도 데이터가 유지돼야 해
 - 모바일에서도 잘 보여야 해"
```

```
"팀원들이 함께 사용할 수 있는 일정 관리 서비스를 만들고 싶어.
 - Google 로그인으로 접속할 수 있어야 해
 - 일정에 댓글을 달 수 있어야 해
 - 이메일 알림도 있으면 좋겠어"
```

#### 유형 2 — 기능 추가 / 수정 요청

기존 프로젝트에 변경 사항을 요청한다. 어떤 기능을 어떻게 바꾸고 싶은지만 설명하면 된다.

```
"로그인 페이지에 소셜 로그인(GitHub, Google)을 추가해줘"
```

```
"상품 목록 페이지 로딩이 너무 느려. 개선해줘"
```

```
"현재 비밀번호가 평문으로 저장되고 있는 것 같아. 보안 취약점 수정해줘"
```

#### 유형 3 — 상태 확인 / 승인 요청

PL Agent가 중간에 사용자에게 방향 확인이나 승인을 요청할 수 있다. 간단히 확인하거나 피드백을 주면 된다.

```
PL Agent: "요구사항을 분석했습니다. React + Node.js 조합으로 진행할까요?
           아니면 특별히 선호하는 기술 스택이 있으신가요?"

사용자: "기술 스택은 알아서 결정해줘. 빠르게 만드는 게 우선이야"
```

```
PL Agent: "1단계(핵심 기능)와 2단계(알림/소셜 기능)로 나눠 진행하려고 합니다.
           1단계 완료 후 확인 후 2단계로 넘어가도 될까요?"

사용자: "좋아. 1단계부터 시작해줘"
```

### 요청 시 도움이 되는 정보

필수는 아니지만, 아래 정보를 함께 전달하면 시스템이 더 정확하게 동작한다.

| 항목 | 예시 |
|---|---|
| 사용 대상 | "사내 직원용", "일반 소비자 대상" |
| 예상 규모 | "동시 사용자 100명 이하", "하루 수천 건 처리" |
| 기술 제약 | "Python만 써야 해", "AWS는 사용 불가" |
| 우선순위 | "속도보다 안정성이 중요해", "빠른 출시가 먼저" |
| 참고 자료 | 화면 캡처, 기존 코드, 유사 서비스 링크 |

## 내부 동작: 시스템은 어떻게 작동하는가

사용자의 요청이 들어온 뒤 시스템이 어떤 순서로 작동하는지 단계별로 설명한다.

### 전체 처리 흐름

```
[사용자]
    │
    │ 자연어 요청
    ▼
┌─────────────────────────────────────────────────────┐
│                    PL Agent                         │
│  - 요구사항 분석 및 정제                              │
│  - 기능 목록 작성 및 우선순위 결정                    │
│  - 개발 단계(Phase) 분할                             │
│  - 에이전트별 작업 지시서 생성                        │
└────────────────────┬────────────────────────────────┘
                     │
         ┌───────────┼───────────┐
         │           │           │
         ▼           ▼           ▼
  ┌──────────┐ ┌──────────┐ ┌──────────┐
  │Architect │ │  UX      │ │Database  │   ← 설계 단계 (병렬 실행)
  │  Agent   │ │ Agent    │ │ Agent    │
  └────┬─────┘ └────┬─────┘ └────┬─────┘
       │             │             │
       └─────────────┼─────────────┘
                     │ 설계 산출물 취합
                     ▼
             ┌──────────────┐
             │ Coding Agent │   ← 구현 단계
             └──────┬───────┘
                    │
          ┌─────────┴─────────┐
          │                   │
          ▼                   ▼
   ┌──────────┐        ┌──────────┐
   │ QA Agent │        │  Review  │   ← 검증 단계 (병렬 실행)
   └────┬─────┘        │  Agent   │
        │              └────┬─────┘
        └────────┬──────────┘
                 │ 수정 요청
                 ▼
         ┌──────────────┐
         │ Coding Agent │   ← 수정 반복 (통과할 때까지)
         └──────┬───────┘
                │ 검증 완료
                ▼
        ┌──────────────┐
        │ DevOps Agent │   ← 배포 단계
        └──────┬───────┘
               │
               ▼
   ┌─────────────────────┐
   │ Documentation Agent │   ← 문서화 단계
   └─────────────────────┘
               │
               ▼
           [완료 보고]
              사용자
```

### 단계별 내부 동작 상세

#### 1단계 — 요구사항 분석 (PL Agent)

사용자의 요청을 받은 PL Agent는 가장 먼저 요구사항을 파싱하고 구조화한다.

- 명시된 기능과 암묵적으로 기대되는 기능을 구분하여 정리
- 기능 간 의존 관계를 파악하고 개발 가능한 단위로 분해
- 불명확한 요구사항은 사용자에게 재질의(최소 횟수로)
- 개발 단계를 나누고 각 단계의 목표와 완료 기준 정의
- 에이전트별 작업 지시서(`task-breakdown.md`) 생성

```
[PL Agent 내부 처리 예시]

입력: "쇼핑몰 만들어줘. 상품 등록, 장바구니, 결제 기능 필요해"

출력:
  Phase 1: 상품 조회 및 장바구니
    - Architecture Agent → 시스템 설계 요청
    - UX Agent         → 상품 목록/상세/장바구니 화면 설계 요청
    - Database Agent   → 상품/장바구니 스키마 설계 요청

  Phase 2: 회원 및 결제
    - Architecture Agent → 인증/결제 연동 설계 요청
    - UX Agent         → 로그인/결제 화면 설계 요청
    - Database Agent   → 회원/주문 스키마 설계 요청
```

#### 2단계 — 설계 (병렬 실행)

PL Agent의 지시를 받은 세 에이전트가 동시에 작업을 시작한다.

**Architecture Agent**
- 전체 시스템 구조 다이어그램 작성
- 기술 스택 선정 및 근거 문서화
- API 엔드포인트 계약 정의
- Coding Agent가 따를 설계 원칙 수립

**UX Agent**
- 사용자 흐름(User Flow) 설계
- 각 화면의 레이아웃과 컴포넌트 명세 작성
- 디자인 시스템(색상, 폰트, 간격 규칙) 정의

**Database Agent**
- 엔티티 관계 다이어그램(ERD) 설계
- 테이블 스키마 및 인덱스 전략 수립
- 초기 마이그레이션 스크립트 작성

> 세 에이전트의 산출물이 모두 준비되면 PL Agent가 상호 충돌 여부를 검토하고 취합하여 Coding Agent에 전달한다.

#### 3단계 — 구현 (Coding Agent)

설계 문서 세 가지를 모두 참조하여 코드를 작성한다.

- Architecture 명세에 따라 디렉토리 구조 및 레이어 구성
- DB 스키마를 기반으로 모델 및 마이그레이션 코드 작성
- UX 명세에 따라 화면 컴포넌트 및 스타일 구현
- 기능 단위로 커밋하여 추적 가능성 확보
- 구현 완료 후 QA Agent와 Review Agent에 동시에 검토 요청

#### 4단계 — 검증 (병렬 실행)

**QA Agent**
- 요구사항 명세를 기반으로 테스트 케이스 작성
- 단위 테스트(Unit) → 통합 테스트(Integration) → E2E 테스트 순서로 실행
- 실패한 테스트를 버그 리포트 형식으로 정리
  - 버그 ID, 재현 절차, 예상 결과, 실제 결과, 심각도 포함
- Coding Agent에 수정 요청 전송

**Review Agent**
- 코드 스타일 및 컨벤션 위반 탐지
- 알고리즘 복잡도, 불필요한 반복, 메모리 누수 등 성능 이슈 검토
- OWASP Top 10 기반 보안 취약점 스캔
- 우선순위(Critical / High / Medium / Low)와 함께 수정 요청 전송

#### 5단계 — 수정 루프

QA Agent와 Review Agent의 피드백이 모두 Coding Agent로 전달된다. Coding Agent는 수정 후 재검증을 요청하며, 모든 Critical/High 이슈가 해소될 때까지 이 루프가 반복된다.

```
Coding Agent ──수정 완료──▶ QA Agent
                        ▶ Review Agent
         ◀──재수정 요청── (이슈 발견 시)
         
이슈 없음 → 다음 단계로 진행
```

#### 6단계 — 배포 (DevOps Agent)

코드가 검증을 통과하면 DevOps Agent가 배포를 담당한다.

- CI 파이프라인 실행 (빌드 → 자동 테스트 → 정적 분석)
- 스테이징 환경 배포 및 스모크 테스트
- PL Agent에 스테이징 배포 완료 보고 (사용자 확인 요청 가능)
- 승인 후 프로덕션 배포 실행
- 배포 후 모니터링 지표 확인 및 이상 시 자동 롤백

#### 7단계 — 문서화 (Documentation Agent)

배포가 완료되면 Documentation Agent가 각 에이전트의 산출물을 취합하여 문서를 생성한다.

- 구현된 API 명세 기반으로 API 레퍼런스 문서 생성
- 변경된 기능을 CHANGELOG에 추가
- 설치/실행 방법 README 업데이트
- 사용자 가이드 신규 기능 반영

---

### 상태 전이 요약

| 단계 | 활성 에이전트 | 완료 조건 |
|---|---|---|
| 요구사항 분석 | PL | 기능 목록 및 작업 지시서 완성 |
| 설계 | Architecture + UX + Database | 3개 설계 산출물 충돌 없이 완성 |
| 구현 | Coding | 모든 기능 구현 및 빌드 성공 |
| 검증 | QA + Review | Critical/High 이슈 0건 |
| 수정 | Coding | 재검증 통과 |
| 배포 | DevOps | 프로덕션 배포 성공 및 모니터링 정상 |
| 문서화 | Documentation | 모든 문서 최신화 완료 |

## 에스컬레이션 규칙

에이전트가 독단적으로 결정하기 어려운 상황에서는 아래 기준에 따라 상위로 보고한다.

| 상황 | 보고 대상 |
|---|---|
| 설계 간 충돌 발생 | PL Agent → 사용자 |
| 요구사항 범위를 벗어난 기능 필요 | PL Agent → 사용자 |
| Critical 버그 해소 불가 | QA Agent → PL Agent → 사용자 |
| 보안 취약점 수정 시 아키텍처 변경 필요 | Review Agent → Architecture Agent → PL Agent |
| 배포 중 장애 발생 | DevOps Agent → PL Agent → 사용자 |

## 산출물 구조

작업이 완료되면 아래 구조의 산출물이 생성된다.

```
project/
├── docs/
│   ├── requirements.md        # 기능 요구사항 명세 (PL)
│   ├── project-plan.md        # 개발 계획 및 일정 (PL)
│   ├── architecture.md        # 시스템 아키텍처 (Architecture)
│   ├── tech-stack.md          # 기술 스택 명세 (Architecture)
│   ├── api-contract.md        # API 인터페이스 명세 (Architecture)
│   ├── ux-flow.md             # 사용자 흐름도 (UX)
│   ├── design-system.md       # 디자인 시스템 가이드 (UX)
│   ├── db-design.md           # DB 설계 및 ERD (Database)
│   ├── test-cases.md          # 테스트 케이스 목록 (QA)
│   ├── test-results.md        # 테스트 결과 및 커버리지 (QA)
│   ├── bug-report.md          # 버그 목록 (QA)
│   ├── review-report.md       # 코드 리뷰 결과 (Review)
│   ├── ci-cd-pipeline.md      # CI/CD 구성 설명 (DevOps)
│   └── infra.md               # 인프라 구성 (DevOps)
├── src/                       # 소스 코드 (Coding)
├── migrations/                # DB 마이그레이션 스크립트 (Database)
├── tests/                     # 테스트 코드 (QA)
├── .github/workflows/         # CI/CD 파이프라인 (DevOps)
├── README.md                  # 프로젝트 가이드 (Documentation)
└── CHANGELOG.md               # 변경 이력 (Documentation)
```
